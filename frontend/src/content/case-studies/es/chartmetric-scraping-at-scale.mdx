## El Problema

El producto de Chartmetric depende de datos frescos y completos de cada plataforma musical importante. Estas plataformas no ofrecen APIs para los datos que necesitamos — o sus APIs tienen rate-limits que las hacen inútiles. El único camino es el web scraping a gran escala, pero cada plataforma lo combate activamente con defensas anti-bot cada vez más sofisticadas.

La empresa necesitaba a alguien capaz de romper cualquier barrera, mantener pipelines funcionando a escala, y recuperarse rápido cuando las plataformas cambiaran sus defensas.

## Ticketmaster — El Imposible

Ticketmaster es ampliamente considerado el sitio web más difícil de scrapear en internet. Sus defensas anti-bot están entre las más agresivas de la industria. Antes de mi llegada, Chartmetric no tenía datos de Ticketmaster.

Lo hice posible. El pipeline ahora extrae datos de eventos y tickets de forma confiable a escala. Cuando sus defensas evolucionan, el scraper también. Flujo continuo de datos desde el lanzamiento.

## Discogs — El Rompecabezas de 7 Meses

Otro ingeniero había intentado resolver Discogs durante 7 meses sin éxito. El desafío central es un problema de coordinación — necesitas orquestar 5 scrapers para consumir dentro de las reglas de rate-limiting de Discogs simultáneamente. Es esencialmente un problema de optimización matemática: cada scraper necesita respetar límites por endpoint y globales mientras maximiza el throughput colectivo.

Resolví el problema de coordinación y construí el pipeline de datos de precios para el marketplace de Discogs, desbloqueando una nueva fuente de ingresos para la empresa.

## TikTok — Recuperación de Apagón Total

El pipeline de ingesta de usuarios de TikTok se apagó completamente — cero datos fluyendo durante semanas. La plataforma había desplegado nuevas medidas anti-scraping que rompieron completamente el enfoque existente.

El scraping de TikTok requiere un conocimiento profundo de la plataforma — cookies, harvesting, endpoints, consumo de API, mapeo de requests. El desafío no es solo entrar, es mantenerse dentro a escala mientras se gestiona el throttling.

Restauré el flujo completo de datos y reduje los costos de proxy de **$1,500/mes a $50/mes** — una reducción del 97% logrando tasas de éxito más altas que antes.

## Tunefind — API + HTML a Escala

Tunefind parece simple en la superficie — alinear datos de API con scraping HTML para enriquecimiento. En la práctica, requiere una infraestructura masiva para mantener. Dos pipelines legacy (PostgreSQL y ClickHouse) necesitaban consolidarse, y el pipeline unificado necesitaba alertas apropiadas y verificaciones de calidad de datos para detectar desajustes entre fuentes API y HTML.

Consolidé ambos pipelines legacy en un solo pipeline confiable con observabilidad completa.

## Shazam — Millones de Requests, Bien Hechos

Shazam es un tema de escala. Millones de requests fluyendo diariamente — hecho bien, funciona suave y barato. Hecho mal, cuesta $5,000 al día en proxies. La diferencia está en la arquitectura y la disciplina de costos.

Construí el pipeline que alimenta datos tanto a PostgreSQL como a ClickHouse. En el camino, diagnostiqué y corregí un bug de corrupción de timestamps que había distorsionado datos silenciosamente en Snowflake durante meses.

## Genius — Throttling de Precisión

Genius es fuerza bruta — pero fuerza bruta precisa. Empujar demasiado fuerte y el pipeline se rompe. Empujar muy poco y los datos llegan tarde. El desafío es encontrar y mantener el balance exacto de throttling, implementando presupuesto inteligente por token de API para maximizar el throughput justo al borde de lo que la plataforma permite.
